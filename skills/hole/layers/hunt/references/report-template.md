# 漏洞报告模板（14 项 · 补天/国内 SRC 通用）

> 用法：整段复制到新文件，逐项替换 `[方括号]` 内容。**第 8 项禁止出现 URL/IP/路径**。等级按「已证明的事实」填，禁止虚报。

---

## 1. 厂商名称
`[工商注册全称，与 ICP 备案主体一致]`

> 取自官网页脚版权行或 ICP 备案查询，不要用产品品牌名（品牌名 ≠ 厂商主体）。

## 2. 域名或 ip
`[主域名，如 example.com]`

> 不要填带 www 的具体子域，平台按主域归属。填完先 nslookup 确认能解析，OCR 抄错域名是常见开局事故。

## 3. 漏洞类型
`Web漏洞` ／ `IoT漏洞` ／ `工程漏洞` ／ `操作系统及通用软件漏洞`

> Web 应用与接口一律选「Web漏洞」；硬件固件、摄像头、路由器选 IoT；工控 SCADA 选工程漏洞。

## 4. 漏洞标题
`[主体简称] + [系统名称] + [漏洞性质] + [后果]`

> 公式示例：`XX公司 M-ERP 登录接口无失败锁定且二次验证可留空，存在撞库风险`。
> 不要写「某系统存在漏洞」这种无信息标题；标题里不要出现攻击成功类表述。

## 5. 漏洞 URL
```
https://[host]/[path]
```

> 多个同构主机逐行列出（3 台以内建议全列）；带参数的写全 `?id=1`；
> 若为 POST 接口，URL 填接口地址，参数在第 9 项 PoC 里给出。

## 6. 漏洞类型
`事件型` ／ `通用型`

子类（按平台下拉框选一个）：`XSS` `配置错误` `弱口令` `入侵事件` `疑似被黑` `文件上传` `逻辑漏洞` `存在后门` `代码执行` `命令执行` `SQL注入` `解析漏洞`

> 判定口径：
> - 遗留调试文件 / 目录列举 / 敏感信息暴露 / 响应头缺失 → **配置错误**
> - 无锁定、无验证码、默认口令、可撞库 → **弱口令**（若核心是校验逻辑缺陷 → **逻辑漏洞**）
> - 越权读取、支付金额篡改、任意改密 → **逻辑漏洞**
> - 反射/存储型脚本执行 → **XSS**；SQL 注入 → **SQL注入**；上传 getshell → **文件上传**
> - 单实例偶发问题选「事件型」，影响同类产品线/多租户批量选「通用型」

## 7. 漏洞等级
`低危` ／ `中危` ／ `高危`

> 硬门槛：**能直接取得权限或敏感数据** 才给高危。
> - 只有「无锁定/可泄露」证据，未进入系统 → 中危封顶；
> - 已进入后台且能横向取数 → 高危；能直接命令执行 → 严重（若平台有该档）。
> 虚报高危会被降级并影响后续提交可信度，宁可如实中危。

## 8. 简要描述
`[2-4 句：漏洞在哪个环节、什么性质、泄露/获取了什么类别信息、会造成什么后果、影响面多大]`

> **禁止**出现 URL、IP、绝对路径、具体文件名参数值——这些放第 5、9 项。
> 写法范式：`某系统某接口未做某校验，未授权可[现象]，泄露[信息类别]，可被用于[后续风险]；该问题在 N 台主机/多租户批量存在。`

## 9. 详细细节

### （1）测试/复现过程与影响范围
```
步骤 1：[请求方法 + 路径 + 关键参数]
步骤 2：[服务端返回的关键状态码与字段]
步骤 3：[重复/变体验证，写明次数与结果一致性]
```
影响范围：`[受影响主机数量、是否多租户同构、涉及的数据类别]`

> 要求：可被第三方独立重放。写清「无需登录 / 无需参数」这类前置条件，审核据此判定可利用性。

### （2）证明截图（必须本地上传，禁止外链粘贴）
| 编号 | 截图内容 | 必备要素 |
|---|---|---|
| 1 | 漏洞完整复现过程 | 地址栏 URL 可见 + 响应关键字段可见 + 浏览器/工具界面完整 |
| 2 | 厂商归属证明 | 官网页脚同时可见：公司全称、ICP 备案号、公安联网备案号（三者同框最有说服力） |
| 3 | 系统时间证明（建议） | 任务栏时间，证明测试时间点 |
| 4 | 关键对比（如有） | 如「留空报错 vs 填写报错」「有防护 vs 无防护」的并列对比 |

> 缺第 1、2 张必被驳回。截图不要打码到看不出域名，也不要用外链图床。

### （3）使用的组件
`[逐项列出：浏览器、curl、Burp Suite、sqlmap、frida 等，附官方下载地址]`

> 模板句式：`仅使用浏览器与 curl（https://curl.se/download.html），未使用组态软件或远程调试工具。`
> 用到商业工具（如 Burp Pro）写清版本；用到自研脚本在第 9(4) 给出。

### （4）PoC / Exploit
```bash
#!/usr/bin/env bash
# 用途：[一句话，说明只验证存在性、不做破坏性动作]
# 用法：./poc.sh https://[host]
set -u
HOST="${1:?usage: poc.sh https://host}"
# [核心请求 + 命中特征判定]
# 命中则打印 leaked fields / 关键证据，不打印任何业务数据
```

> 硬要求：思路清晰、可读性高、能独立复现；**只证明存在，不导出业务数据、不写入、不删除**；
> 涉及口令验证的脚本，必须只用固定错误口令，注释里明确「不进行口令猜测」。

## 10. 修复方案
1. `[立即缓解措施：删除文件/关闭接口/加白名单]`
2. `[根本修复：校验逻辑/参数化查询/权限判定]`
3. `[加固：限速、锁定、验证码升级、错误信息收敛]`
4. `[流程：CI 扫描、上线检查项、测试生产隔离]`

> 按「立即—根本—加固—流程」四层写，比笼统一句「建议修复」更容易被厂商采纳并确认。

## 提交前自检

| 项 | 检查点 |
|---|---|
| 第 8 项 | 通读一遍，确认无 URL / IP / 路径 / 参数值 |
| 截图 | 复现截图 + 归属证明截图齐全，均本地文件上传 |
| 归属证明 | 公司全称 + ICP + 公安备案三者同框 |
| 等级 | 与证据强度匹配，未进入系统不报高危 |
| 合并 | 多主机同构问题写在一条内，不拆条刷量 |
| 表述 | 只写「存在什么缺陷」，不写「已完成攻击/已获取数据」 |
